THE MAIN WORKFLOW

一轮标定，六个阶段

先固定实验与数值条件，再分析与搜索，最后重载候选并验收。点击阶段查看输入、动作、输出和流程边界。

01 / DEFINE

先固定问题，再开始求解

准备实测数据与基线资产，检查参数定义和实验设置的一致性。冻结 Template，并保存输入身份、配置和依赖版本。

EvidenceAssetTemplateParameters
01 / 06
输入
训练 / 验证观测、基线参数、固定实验与数值条件。
动作
Evidence.prepare() → Asset.load_or_create() → Template.resolve()/freeze()。
输出
resolved.json 与输入身份；Parameters 的最终搜索映射在参数分析后冻结。
进入下一阶段之前基线参数必须一致；待标定参数与固定参数不得重叠；训练和验证采集组必须分开。

refinement 使用显式声明的数值或离散化加密配置，比较观测特征差异。结论仅覆盖所声明的加密设置；没有配置加密项时不能通过默认资格检查。

流程顺序：准备与冻结 → 基线和数值资格检查 → 灵敏度及可辨识性分析 → 搜索循环 → 重载、训练复测、验证及数值复测 → 发布与记录。检查失败或预算耗尽时可能提前结束。

ONE EVALUATION PATH

不同阶段，复用同一条评估路径

基线、数值检查、灵敏度分析、搜索和最终验证，共用参数解码、仿真与评分机制。下图以搜索的一批候选为例；所有调用由 Tuning 编排。

每批工作先经 Decision 授权
Optimizer.ask提出搜索空间中的一批候选TrialBatch · [B, K]
Parameters.decode转为带单位的物理参数，检查边界parameter_values · [B, P]
Rollout.execute_batch构建环境、回读参数、执行并记录状态Episode / Trace
Evaluator.score_batch使用观测、掩码、尺度和权重计算评分loss · metrics · constraints
Optimizer.tell接收 BatchResult 并更新搜索状态Decision 再决定继续或停止
↶ 继续搜索时返回 ask；失败或缺失观测保留失败状态，不作为零损失。B = 候选数，K = 搜索维数，P = 物理参数数。

普通执行 · Environment

每个 trial × experiment × repeat 创建独立环境。capacity 控制线程池并发量，避免复用上一次仿真的状态。

批量执行 · BatchEnvironment

Asset 实现 create_batch_environment() 时启用。每个实验与重复内按 worlds 分块，共同仿真多个候选；具体并行方式由适配器实现。

STOPPING ≠ ACCEPTANCE

为什么停止，与是否通过，分别回答。

Decision 停止搜索后，Tuning 检查是否具备可验收候选。符合前置条件才进入导出、重载与最终验证；验证失败不会自动启动新一轮训练。

termination_reason

搜索为什么结束？

例如达到目标、预算耗尽、停滞或候选空间遍历完成。即使出现 target_reached，仍然需要完成验收。

acceptance

候选是否可以发布？

由训练复测、验证与数值复测等检查确定。可能为 accepted、rejected_training、rejected_validation、rejected_numerics 或其他未完成 / 失败状态。

仅 acceptance == "accepted" 时写入 release/。没有验证数据或最终验证预算不足时，不能将候选作为已验收资产发布。

TRACEABLE BY CONSTRUCTION

运行结束，留下的不只是参数。

Tuning 统一更新 RunState，记录输入身份、工作预算、分析结论、批次与决策历史。Play 在存在基线与候选轨迹时生成对比；展示异常单独记录。

核心与求解器解耦。接入新案例时组合成员、实现 Asset / Environment 接口，继续使用同一套生命周期。

02

THE TUNING MODULE

10 个成员，各自承担一项明确职责

Tuning 组合这些成员并统一编排。核心独立于 Newton；线缆案例通过 Asset 与仿真适配器接入 Newton VBD，沿用同一条生命周期。

成员定义来自线缆报告的 Tuning 章节；接口分工按当前实现整理。成员名称可打开对应源码。
成员主要职责接口与边界
Evidence管理实测观测、物理时间、掩码、尺度、权重，以及训练 / 验证采集组。prepare() 校验并整理证据；原始视频和遥操数据先经预处理或适配。
Asset定义模型与参数绑定，创建新环境，支持候选资产导出与重载。create_environment()、可选批量接口、export()/reload()；环境提供实际参数回读。
Template固定实验条件、数值设置、离散化及固定参数，声明资格检查方式。resolve()/freeze()、instantiate()、refined()；搜索中不原地修改配置。
Parameters管理名称、单位、边界、基线、线性 / 对数变换及搜索组合方向。encode()/decode()；分析后冻结映射。当前参数为连续标量。
Rollout执行 trial × experiment × repeat，检查参数回读，收集轨迹与失败状态。execute_batch()；普通环境走线程路径，支持批量接口的 Asset 走 BatchEnvironment。
Evaluator按观测协议批量计算损失、指标、约束、分析特征及有效性。score_batch()；保留失败与缺失语义，评分不能把缺失数据当作零误差。
Optimizer提出候选、接收评分，更新搜索状态与诊断；内置 GridSearch / CMA-ES。initialize()/ask()/tell()；提供事实诊断，继续或停止交给 Decision。
Decision统一管理工作预算、目标和停止条件，授权继续或停止。next_action()；覆盖资格检查、分析、搜索与最终评估的工作授权。
Validator对重载且冻结的候选执行训练复测与验证阈值检查。validate() 使用 Tuning 提供的评估回调；候选重载由 Asset 负责。
Play消费已保存的轨迹，生成标定前后对比、回放及展示产物。compare()/export_usd()；通用 USD 输出是点轨迹动画，不是完整物理资产。

Tuning 拥有唯一的 RunState

RunState 记录输入身份、阶段、预算、批次、最优候选、分析与验收结论，由 Tuning 统一更新。它是运行状态，不是第 11 个功能成员。灵敏度和可辨识性分析同样属于 Tuning。

实现能力与结论范围

内置优化器为 GridSearch 与 CMA-ES，自动断点续跑尚未实现。具体求解器的设备、并行能力和数值精度需要案例验证；合成示例的成功不代表真实线缆已通过验收。

03

FROM INTENT TO AN EXECUTABLE CASE

Skills 把需求装配为可运行的 Tuning

五个 Skills 是供编码助手使用的配置与实现指引。它们读取证据、澄清关键未知项、维护一份案例规格，并生成真实的工厂与运行入口；运行时仍由 task_tuning 负责。

统一入口

standard-tuning

汇总目标、证据和已确认决策，明确本次是设计、构造还是执行。维护共享的 TUNING-SPEC.md，按未解决的问题调用相关专项 Skill，并交付真实的 Tuning 实例工厂。

↓ 按需处理相关问题；三类专项工作不要求固定先后顺序

tuning-evidence

定义观测与预处理、采集组划分、损失 / 掩码 / 尺度、验证指标和验收阈值。

EvidenceEvaluatorValidator

tuning-environment

明确物理边界、实验条件、数值资格、实际参数绑定、并行执行和轨迹展示。

AssetTemplateRolloutPlay

tuning-search

确定参数边界与组合、可辨识性要求、搜索策略、全流程预算和停止条件。

ParametersOptimizerDecision

tuning-adapter

仅在现有类型无法表达需求时

补充最小成员子类或求解器适配器，满足环境、评分、优化、验证或展示契约。能通过现有构造参数表达的需求直接配置；适配器继续复用 Tuning.run()。

  1. ① TUNING-SPEC.md

    记录事实、决策、假设、来源和十个成员的选型。

  2. ② build_tuning(workspace=…)

    生成可导入的案例工厂；每次返回新的真实 Tuning。

  3. ③ 构造与静态检查

    核对类型、基线、实验 ID、数据形状、路径与依赖；不执行仿真。

  4. ④ tuning.run()

    在执行范围与预算已明确时调用一次，进入本页第一部分的流程。

调用示例：先构造，不启动仿真

$standard-tuning
根据已有资产说明和实测数据创建标定案例。
先检查证据，澄清尚未确定的实验条件。
交付 TUNING-SPEC.md 和 build_tuning(workspace=...)。
本次只构造并检查实例，不调用 prepare() 或 run()。

交付后的运行入口

以下假设案例已生成 build_tuning.py，且执行范围与预算已经确认：

from build_tuning import build_tuning

if __name__ == "__main__":
    tuning = build_tuning(workspace="workspace")
    result = tuning.run()
    print(result.termination_reason)
    print(result.acceptance)

构造与执行的边界：导入或构造实例不运行仿真；prepare() 会执行基线与数值资格检查，不能当作静态检查，也不能先调用它再调用 run()。每次运行使用新实例与独立运行目录。

04

TWO WAYS TO USE TASKTUNING

独立完成标定，也能作为 Agent 的精调工具

两种方式共享同一套运行核心。区别在于：任务定义是已经明确，还是由外层 Agent 在仿真重建过程中逐步形成。每次进入 Tuning 时，都需要一个明确、可检查的任务定义。

01 / STANDALONE CALIBRATION

任务明确，直接构造并运行

当候选参数、实验设置、观测方式与标定流程已经确定，可以直接初始化一个 Tuning 对象，或通过 standard-tuning Skill 生成案例工厂。

如果还缺少单位、参数范围、边界条件或验收阈值等关键信息，Agent 可以通过证据检查与问答补齐，再完成构造与运行。

例如：机器人模型与辨识实验已确定，需要辨识选定关节的惯性、摩擦或其他模型参数。
明确需求 / 补齐信息 → 配置十个成员
→ 构造 Tuning → run() → 标定结果

02 / EMBEDDED IN AN AGENT WORKFLOW

外层定义问题，内层精调参数

自动仿真重建时，模型假设、需要标定的参数和实验设置可能尚不明确。外层 Agent 先结合证据提出可检验的任务，再将 TaskTuning 作为工具式子流程调用。

Agent 给出模型与设置、候选参数及范围、evidence、metric 和预算；TaskTuning 在这些约束下完成精细调整，返回参数、运行结论和诊断产物。

例如：重建接触或柔性物体行为时，Agent 先选择模型与待调参数，再用 Tuning 检验该假设下的拟合能力。
Agent 定义结构化任务 → TaskTuning
→ 结果与诊断 → Agent 决定后续动作

放入“校准与评估主线”的哪个位置？

TaskTuning 主要承接 ④ 精细调整，向后续效果与原因诊断提供候选、评分与分析记录。外层仍保留模型选择、采集决策和最终准入的职责；一次 Tuning 调用不替代整个 Agent 工作流。

外层 · 形成任务

①② 数据门与测量
③ 参数初估

质量检查与观测定义；检索来源、提出模型假设和参数中心值 / 范围，明确实验设置、评分协议及预算。

交付：经过代码校验的结构化 Tuning 任务。

内层 · 有界求解

④ TaskTuning 精细调整

实例化真实成员，检查数值条件与局部可辨识性，在冻结的模型、证据和评分协议内搜索参数。

Decision 授权 → Optimizer.ask
→ 仿真与评分 → Optimizer.tell
→ 停止、重载、按约定验证

外层 · 判断下一步

⑤⑥ 效果与原因诊断
⑦ 采集 · ⑧⑨ 判定与准入

结合候选与诊断，判断参数偏差、观测映射问题、模型缺口或证据不足。按外层标准决定重试、补数据、形成缺口报告或准入。

↶ 需要修改模型、参数范围、evidence 或 metric 时，由外层创建新任务与新的 Tuning 实例，再进入精调。历史运行保留；一次运行内不悄悄改变问题定义。

输入：Agent 提供结构化任务

模型与绑定
资产 / 模型版本、参数到求解器的绑定、可用环境接口 → Asset。
候选参数空间
参数名、单位、基线、上下界、变换与固定参数划分 → Parameters / Template。
实验与数值设置
初始状态、控制 / 边界、采样时刻、时间步、离散化、资格检查方式 → Template。
Evidence
训练数据引用、观测对应关系、采集组、预处理来源及验证安排 → Evidence。
Metric 与验收
损失、掩码、尺度、权重、特征、阈值及适用范围 → Evaluator / Validator。
策略与预算
优化器、批量执行设置、试验 / 仿真 / 时间限制及停止条件 → Optimizer / Rollout / Decision。

输出：结果对象 + 诊断产物

TuningResult 直接提供：

  • parameters：选出的候选参数；没有候选时为空。
  • termination_reason：本轮为何停止。
  • acceptance：本轮验收状态。
  • asset_path：通过验收时发布的资产路径。
  • run_directory：可追溯运行目录。

外层通过运行产物取得批次评分、轨迹 / 特征、灵敏度与可辨识性报告、验证和数值检查记录；所需残差摘要由外层或案例适配器按评分协议整理。

职责分界：Tuning 给出固定任务下的求解结果；“模型是否合适、是否需要新实验、是否准入知识库”由外层综合判断。

接入约定：共享生命周期，明确外层边界

任务转实例：上述输入是任务契约说明，当前没有内置的通用 JSON 任务编译器或已注册的 Agent tool 服务。接入时由案例工厂 / 外层适配代码转换为十个真实成员，再调用 Tuning.run()。

候选与停止：外层 Agent 指定参数空间与策略；默认由内层 Optimizer 提出每批具体候选，Decision 执行本轮预算和停止规则。若需 Agent 逐步提出候选，应通过符合现有契约的 Optimizer 适配接入。

留出数据与最终判定：参考主线要求 Agent 不访问留出数据；该隔离及允许返回的信息需要外层可信 harness 实现，TaskTuning 本身不提供访问隔离。若验证完全放在外层，本轮没有内部验证数据时应保留 unvalidated，由外层另行记录最终判定，不能将它自动改写成内部 accepted。

避免验证泄漏：一旦验证结果被用来修改模型或配置，这些数据就成为开发证据，后续仍需独立留出验证。参考主线中的统计判定、审查和知识库准入也属于外层能力，不是当前通用 Validator 的内置功能。
