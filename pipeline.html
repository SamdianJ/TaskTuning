Agent-driven calibration.
One traceable runtime.

The outer agent turns evidence and model hypotheses into a checkable calibration task. A single Tuning.run() qualifies, analyzes, searches and validates that task under fixed conditions, then returns results and diagnostics for the agent’s next decision.

Baseline evaluation, numerical qualification, sensitivity analysis, search and final validation share parameter decoding, simulation and scoring. This diagram follows one search batch; Tuning orchestrates every call.

Individual execution · Environment

Create a fresh environment for each trial × experiment × repeat. capacity controls thread-pool concurrency; each episode starts with fresh simulation state.

Batched execution · BatchEnvironment

Enabled when Asset implements create_batch_environment(). Within each experiment and repeat, worlds limits chunk size for simulating multiple candidates together. The adapter determines how they run in parallel.

STOPPING ≠ ACCEPTANCE

Why it stopped. Whether it passed.

After Decision stops search, Tuning checks whether a candidate is eligible for acceptance testing. Only eligible candidates proceed to export, reload and final validation. Failed validation does not automatically restart training.

termination_reason

Why did the search end?

Examples include reaching the target, exhausting a budget, stagnation or exhausting the candidate space. Even target_reached still requires acceptance checks.

acceptance

Can the candidate be released?

Training retests, validation and numerical retests determine the result. Possible states include accepted, rejected_training, rejected_validation, rejected_numerics, and other incomplete or failed states.

Only acceptance == "accepted" permits writing to release/. Without validation data or sufficient final-validation budget, the candidate cannot be released as an accepted asset.

TRACEABLE BY CONSTRUCTION

A run leaves more than parameters.

Tuning updates RunState with input identities, budgets, analysis, batches and decision history. Play generates comparisons when baseline and candidate traces exist; presentation errors are recorded separately.

The core is decoupled from the solver. New cases compose members and implement Asset / Environment interfaces while retaining the same lifecycle.

THE TUNING MODULE

10 members, each with a clear responsibility

Tuning composes and orchestrates these members. The core is independent of Newton. The cable case connects Newton VBD through its Asset and simulation adapters while retaining the same lifecycle.

Member responsibilities and interfaces in the supplied pipeline design. Each member has one role within the shared lifecycle.
MemberResponsibilityInterface and boundary
EvidenceManage measured observations, physical times, masks, scales, weights, and training / validation acquisition groups.prepare() validates and prepares evidence. Raw video and teleoperation data require preprocessing or adapters.
AssetDefine the model and parameter bindings, create fresh environments, and export / reload candidate assets.create_environment(), an optional batch interface, and export()/reload(). Environments expose actual applied-parameter readback.
TemplateFix experimental conditions, numerics, discretization and fixed parameters; declare the qualification policy.resolve()/freeze(), instantiate(), refined(). Settings do not change in place during search.
ParametersManage names, units, bounds, baselines, linear / log transforms and search-combination directions.encode()/decode(). Freeze the mapping after analysis. Current parameters are continuous scalars.
RolloutExecute trial × experiment × repeat, check parameter readback, and collect traces and failure states.execute_batch(). Individual environments use threads; assets with a batch interface use BatchEnvironment.
EvaluatorCompute batch losses, metrics, constraints, analysis features and validity under the observation protocol.score_batch(). Preserve failure and missing-data semantics; missing observations cannot become zero error.
OptimizerPropose candidates, consume scores, and update search state and diagnostics. Includes GridSearch / CMA-ES.initialize()/ask()/tell(). Expose factual diagnostics; Decision controls continuation and stopping.
DecisionManage budgets, targets and stopping conditions; authorize continuation or stop.next_action(). Authorize work during qualification, analysis, search and final evaluation.
ValidatorApply training-retest and validation thresholds to a reloaded, frozen candidate.validate() uses the evaluation callback supplied by Tuning. Asset handles candidate reload.
PlayConsume saved traces to produce before/after comparisons, replay and presentation artifacts.compare()/export_usd(). Generic USD output is point-trajectory animation, not a complete physical asset.

Tuning owns the single RunState

RunState records input identities, phases, budgets, batches, the best candidate, analysis and acceptance. Tuning alone updates it. It is runtime state, not an eleventh functional member. Sensitivity and identifiability are also Tuning methods.

Implementation and qualification limits

Built-in optimizers are GridSearch and CMA-ES; automatic resume is not implemented. Solver devices, concurrency and numerical accuracy require case-specific checks. Successful synthetic examples do not establish acceptance of the real cable.

FROM INTENT TO AN EXECUTABLE CASE

Skills turn requirements into an executable Tuning

Five skills provide configuration and implementation instructions for a coding agent. They inspect evidence, clarify consequential unknowns, maintain one case specification, and produce a real factory and entry point. task_tuning remains the runtime.

Shared entry point

standard-tuning

Consolidate goals, evidence and confirmed decisions. Establish whether the scope is design, construction or execution. Maintain one shared TUNING-SPEC.md, route unresolved topics to the relevant specialist skills, and deliver a real Tuning factory.

  1. ① TUNING-SPEC.md

    Record facts, decisions, assumptions, sources and selections for all ten members.

  2. ② build_tuning(workspace=…)

    Produce an importable case factory that returns a fresh, real Tuning on each call.

  3. ③ Construct and inspect

    Check types, baselines, experiment IDs, data shapes, paths and dependencies without simulation.

  4. ④ tuning.run()

    Call once when execution scope and budgets are established, entering the workflow in section 01.

Example prompt: construct without simulation

$standard-tuning
Create a calibration case from the asset description and measured data.
Inspect the evidence first and clarify unresolved experimental conditions.
Deliver TUNING-SPEC.md and build_tuning(workspace=...).
Only construct and inspect the instance; do not call prepare() or run().

The delivered execution entry point

This example assumes the case has generated build_tuning.py and execution scope and budgets have been confirmed:

from build_tuning import build_tuning

if __name__ == "__main__":
    tuning = build_tuning(workspace="workspace")
    result = tuning.run()
    print(result.termination_reason)
    print(result.acceptance)

Construction versus execution: Importing or constructing does not simulate. prepare() executes baseline and numerical qualification, so it is not a static check and must not be called before run(). Each run uses a fresh instance and a separate run directory.

04

TWO WAYS TO USE TASKTUNING

Standalone calibration or an agent fine-tuning tool

Both modes share the same runtime. The difference is whether the task is already defined or is formed by an outer agent during simulation reconstruction. Every Tuning invocation needs a clear, checkable task definition.

01 / STANDALONE CALIBRATION

Defined task: construct and run directly

When candidate parameters, experimental settings, observations and the calibration procedure are already known, initialize a Tuning object directly or use the standard-tuning skill to generate a case factory.

When units, parameter bounds, boundary conditions or acceptance thresholds are missing, the agent can inspect evidence and ask targeted questions before construction and execution.

Example: a robot model and identification experiments are defined, and selected joint inertias, friction or other model parameters need identification.
Define the task / fill gaps → Configure ten members
→ Construct Tuning → run() → Calibration result

02 / EMBEDDED IN AN AGENT WORKFLOW

The outer agent defines; Tuning refines

During automated simulation reconstruction, model assumptions, parameters and experiment settings may still be unclear. The outer agent uses evidence to propose a testable task, then invokes TaskTuning as a tool-like subworkflow.

The agent supplies the model and settings, parameter candidates and bounds, evidence, metrics and budget. TaskTuning refines parameters within those constraints and returns results and diagnostic artifacts.

Example: reconstructing contact or flexible-body behavior. The agent selects a model and tunable parameters, then uses Tuning to test how well that hypothesis fits.
Agent defines a structured task → TaskTuning
→ Results and diagnostics → Agent chooses the next action

Where does it fit in the Calibration & Evaluation Loop?

TaskTuning primarily implements ④ Fine-tuning, providing candidates, scores and analysis for downstream result and root-cause checks. Model selection, data-collection decisions and final admission remain with the outer workflow. One Tuning invocation does not replace that workflow.

Outer workflow · Define the task

①② Data gate and measurement
③ Initial parameter estimate

Check data quality and define observations. Retrieve sources, propose model assumptions and parameter centers / ranges, and specify experiments, scoring and budget.

Deliverable: a structured Tuning task validated by code.

Inner workflow · Bounded solve

④ TaskTuning fine-tuning

Instantiate real members, qualify numerics and analyze local identifiability, then search within a frozen model, evidence and scoring protocol.

Decision authorizes → Optimizer.ask
→ Simulate and score → Optimizer.tell
→ Stop, reload, validate as specified

Outer workflow · Choose the next action

⑤⑥ Result and root-cause checks
⑦ Collection · ⑧⑨ Verdict and admission

Use candidates and diagnostics to distinguish parameter bias, observation-mapping issues, model gaps and insufficient evidence. Apply outer-workflow criteria to retry, collect data, report a gap or admit the result.

↶ To change the model, parameter bounds, evidence or metric, the outer workflow creates a new task and a fresh Tuning instance. Retain previous runs; do not silently redefine the problem during a run.

Input: an agent-defined structured task

Model and binding
Asset / model revision, parameter-to-solver bindings and available environment interfaces → Asset.
Parameter space
Names, units, baselines, bounds, transforms, and fixed versus calibrated parameters → Parameters / Template.
Experiment and numerics
Initial state, controls / boundaries, sampling times, timestep, discretization and qualification policy → Template.
Evidence
Training-data references, observation correspondence, acquisition groups, preprocessing provenance and validation arrangements → Evidence.
Metrics and acceptance
Loss, masks, scales, weights, features, thresholds and qualification scope → Evaluator / Validator.
Strategy and budget
Optimizer, batch execution settings, trial / rollout / time limits and stopping conditions → Optimizer / Rollout / Decision.

Output: result object + diagnostic artifacts

TuningResult directly provides:

  • parameters: selected candidate parameters, or none when no candidate exists.
  • termination_reason: why this run stopped.
  • acceptance: the acceptance status of this run.
  • asset_path: the released asset path when accepted.
  • run_directory: the traceable run directory.

Run artifacts provide batch scores, traces / features, sensitivity and identifiability reports, validation and numerical checks. The outer workflow or case adapter prepares any residual summaries according to the scoring protocol.

Responsibility boundary: Tuning solves a fixed task. The outer workflow judges model suitability, the need for new experiments and knowledge-base admission.

How this relates to the calibration experiments

The plug experiment illustrates why model diagnosis belongs in the outer loop: direct fitting exposed mismatches, CAE identified a missing metal-contact load, and the revised model required a new calibration task. The cable experiment likewise changed model assumptions across separate stages.

These examples motivate the design; they are not evidence that the entire experiment history was executed autonomously by an agent. The experiment reports retain their own acceptance and qualification outcomes.

Integration contract: one lifecycle, explicit outer responsibilities

Task to instance: These inputs describe a task contract. There is currently no built-in generic JSON task compiler or registered agent tool service. A case factory or outer adapter maps them to ten real members, then calls Tuning.run().

Candidates and stopping: The outer agent specifies the parameter space and strategy. By default, the inner Optimizer proposes each concrete batch, and Decision enforces run budgets and stopping rules. An agent that proposes candidates step by step needs an Optimizer adapter conforming to the existing contract.

Held-out data and final verdict: The reference workflow prevents agents from accessing held-out data. A trusted outer harness must enforce that isolation and permitted disclosures; TaskTuning itself provides no access isolation. If validation is entirely external and the run has no internal validation data, retain unvalidated and record the external verdict separately. Do not automatically rewrite it as internal accepted.

Avoid validation leakage: Once validation results guide model or configuration changes, those data become development evidence and fresh independent validation is needed. Statistical verdicts, review and knowledge-base admission in the reference workflow are outer capabilities, not built-in features of the generic Validator.
